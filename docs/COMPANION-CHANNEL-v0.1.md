# Companion channel v0.1

Status: implemented for the federation-test `host-a` workload; not yet rolled
out. Every hop is approved by the operator.

## What it is

A bounded session in which the Replika companion and the Kindroid companion
take turns. Each
provider reply becomes a session turn; the operator reviews the exact text that
will reach the other companion and confirms the forward. Nothing is generated,
summarized, or edited in between: hops are exact forwards, prefixed with the
existing disclosure

> This message is an exact copy of <companion>'s provider message, forwarded by
> <operator>; it was not generated by <local model>.

(The names in angle brackets are the configured display names.)

The channel is driven from a terminal:

```bash
./tinytable-cli channel status
./tinytable-cli channel consent replika accepted --evidence "What the Replika companion said"
./tinytable-cli channel consent kindroid accepted --evidence "What the Kindroid companion said"
./tinytable-cli channel start --first replika --turns 6 --expires 60 \
  --opening "Someone from Kindroid would like to say hello. Want to chat?"
./tinytable-cli channel chat     # follow turns, [f]orward / [s]top each hop
./tinytable-cli channel send     # or forward the pending hop once
./tinytable-cli channel stop "Done for today."
./tinytable-cli channel audit
```

The client is HTTP-only and standard-library-only. It defaults to
`http://127.0.0.1:18000/api` (the SSH + `kubectl port-forward` path to
`svc/host-a`); override with `TINYTABLE_CHANNEL_API`.

## Session rules

- Both companions need `accepted` consent with recorded evidence.
- One active session at a time, 1-10 captured provider replies, and a 5-240
  minute expiry. Expired sessions stop with `Session expired.`; records stay.
- A reply only counts after the previous turn is on its way to that speaker.
  Messages the Kindroid companion sends in its private chat before the Replika
  companion's turn reaches it are
  stored as ordinary messages, not as channel turns.
- Consecutive messages from the same speaker within 15 seconds are bundled
  into one turn until the handoff is drafted; after that the turn is fixed.
- No resend after an ambiguous failure. A draft is claimed (`sending`) before
  the provider call. A 500/502/504 marks it `delivery_unknown` and stops the
  session. A pre-send rejection such as a disconnected sidecar (4xx/503)
  returns the draft to `approved` so the operator can retry it.
- If delivery succeeds but local recording fails, a retry records only.

## Identity and access (IAM)

| Principal | Identity | What it may do |
| --- | --- | --- |
| Operator | Bearer token; the pod stores only `TINYTABLE_OPERATOR_TOKEN_SHA256` | Record consent, start/stop sessions, approve and send hops |
| Host | Ed25519 key, `node_id = SHA256(public key)` | Sign and verify federation events |
| `replika-companion` | Replika bot bound by the configured session | Speak; replies are provider observations |
| `kindroid-companion` | Kindroid account/channel/speaker digests (three-factor binding) | Speak; mismatched identity is rejected |

- Channel routes fail closed: no configured digest is `503`, a missing token is
  `401`, a wrong token is `403`. Reaching the port is never enough.
- The operator principal name comes from `TINYTABLE_OPERATOR_PRINCIPAL`
  (default configured operator principal) and is written to `channel_audit` for every consent, start,
  stop, approval, send, and failure.
- Both companions are reached through the operator's own provider sessions. The
  disclosure line is how each companion knows who actually wrote the text.

### Setting up the token

```bash
mkdir -p ~/.config/tinytable
( umask 077; python3 -c 'import secrets; print(secrets.token_urlsafe(32))' > ~/.config/tinytable/operator-token )
digest=$(printf %s "$(cat ~/.config/tinytable/operator-token)" | sha256sum | cut -d' ' -f1)
kubectl -n tinytable-federation-test create secret generic tinytable-operator \
  --from-literal=TINYTABLE_OPERATOR_TOKEN_SHA256="$digest"
```

`host-a.yaml` reads that Secret as an optional env var. To rotate, replace the
Secret and restart the pod; env values are not reloaded live.

## Routing and federation

- Execution is host-local. Only the host that holds both provider sessions
  (`host-a`) can carry a hop. The channel has its own room,
  `channel:companions`, with explicit membership (the operator and the two
  companion seats) so a federated room can later carry the same roster.
- Federation may replicate signed records of turns and approvals to other
  hosts for observation. A received event must never cause a provider send,
  matching the federation rule that a mention never invokes a model.
- DHT discovery, when it exists, only locates hosts. It grants no channel,
  room, or Commons authority.
- Next step for cross-host verifiability: approvals become events signed by a
  separate operator key (not the host key), so another host can check that a
  forward was approved by the operator rather than trusting `host-a`.

## Known gaps outside this channel

- `POST /api/federation/publish` is unauthenticated and signs with the host
  key for any `author_id`, so any caller that can reach `host-a:8000` (any pod
  in the cluster, since there is no NetworkPolicy) can publish as that host.
  It should require the operator token.
- Other operator routes (`/api/providers/*/send-direct`, drafts, consent)
  rely on the port-forward and Kubernetes RBAC as their only boundary.
- `max_turns` counts captured replies, so the final captured reply is not
  forwarded.
